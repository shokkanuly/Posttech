## 1. Обзор проекта

**JanaMen** — это модульный MVP для хакатона, объединяющее личный профиль сотрудника, кадровые заявки, обязательное обучение и доказательный AI-ассистент в едином удобном рабочем пространстве.

- **Frontend**: Адаптивное Single Page Application (SPA), созданное на базе чистого HTML5, современной дизайн-системы Vanilla CSS (фирменные цвета Jana Post, темная/светлая тема) и Vanilla JavaScript. Без тяжелых сторонних UI-фреймворков.
- **Backend**: Модульный монолит на FastAPI и SQLAlchemy 2.0 ORM с миграциями Alembic и строгим серверным контролем доступа (RBAC).
- **Безопасность и авторизация**: Серверная валидация прав доступа, безопасное хеширование паролей PBKDF2-HMAC и отзывные сессии на базе JWT Bearer токенов.
- **Движок кадровых заявок**: Транзакционное создание заявок (отпуск и аванс), проверка баланса дней, очередь согласования для руководителей и полный журнал истории изменений.
- **Jana Academy (LMS)**: Каталог курсов, просмотр уроков с поддержкой Markdown, интерактивное тестирование с мгновенной проверкой ответов и сохранением прогресса в базе данных.
- **AI Jana (Доказательный AI-ассистент)**: конвейер «защита приватности → ML-поиск (TF-IDF по символьным n-граммам) → опционально Gemini Flash → проверка по источникам». Ответ модели показывается, только если весь текст состоит из точных выдержек процитированных утверждённых источников; иначе показывается точный текст источника или безопасный фоллбэк. Демонстрационные источники явно помечены как синтетические.
- **Границы интеграции**: Документированные адаптеры (Mocked Boundary) для будущей бесшовной интеграции с **1С:ЗУП 3.1** и **Documentolog (ЭДО)**.

## 2. Локальный запуск и быстрая настройка

### Обновления из локальных рабочих копий

Интеграция и фактические результаты проверок описаны в [docs/LOCAL_MERGE_REPORT.md](docs/LOCAL_MERGE_REPORT.md).
Полная хронология этапов развития платформы и архитектурные решения зафиксированы в [docs/PROJECT_HISTORY.md](docs/PROJECT_HISTORY.md).
Основная база — PostgreSQL 17. `docker compose up --build` поднимает базу и приложение; в демо-режиме контейнер сам применяет миграции и создаёт синтетические данные масштаба компании. Для запуска приложения вне Docker с той же базой:

```bash
docker compose up -d db            # PostgreSQL на 127.0.0.1:5432 (порт: POSTGRES_PORT)
python -m app.migrate              # DATABASE_URL из .env.example указывает на эту базу
```

Старый Docker volume с SQLite не переносится: демо-данные синтетические и создаются заново. SQLite по-прежнему подходит для быстрых локальных опытов (`DATABASE_URL=sqlite:///./janamen.db`).
Тесты: `TEST_DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:PORT/TEST_DB python -m pytest -q`.
Каждый тест создаёт собственную схему `janamen_test_<uuid>` и удаляет только её. Схема `public` не очищается.

Gemini выключен по умолчанию. Для подключения нужны `AI_PROVIDER=gemini`, `GEMINI_API_KEY`, доступная модель в `GEMINI_MODEL` и явное разрешение оператора `GEMINI_DATA_SHARING_APPROVED=true` после проверки правил передачи источников внешнему провайдеру.
Вопрос сотрудника остаётся локально. Внешнему провайдеру передаются только отобранные доступные утверждённые фрагменты для выбора дословных цитат. Проверка доступа не заменяет разрешение на внешнюю передачу: оператор должен проверить все доступные источники, включая HR-разделы. Автоматическая очистка персональных данных в самих источниках не заявляется.
Дословно одинаковые релевантные утверждения с разными числовыми значениями приводят к безопасному фоллбэку до вызова провайдера. Общие смысловые противоречия этим правилом не выявляются.
Реальные вызовы Gemini при проверке объединения не выполнялись.

ML: `python -m pip install -r requirements-ml.txt && python -m ml.train && python -m ml.evaluate`.
Режим обученного ранжирования включается через `AI_RETRIEVAL_MODE=ml` и `AI_RETRIEVAL_MODEL_PATH=ml/artifacts/relevance.json`.

Масштабные синтетические данные: `python -m app.seed_scale --employees 150` (только демонстрационная БД).
Измерение: `DEMO_PASSWORD='...' python -m app.benchmark --base-url http://127.0.0.1:8000`.
Замер этого объединения в Docker (PostgreSQL 17, 157 сотрудников, 434 заявки): медиана ключевых вызовов 2.8–15.8 мс, параллельная нагрузка 400 запросов в 16 потоков — 173.0 запросов/с, ошибок: 0 ([benchmark-docker.json](docs/evidence/benchmark-docker.json)). [benchmark-postgresql.json](docs/evidence/benchmark-postgresql.json) — более ранний замер вне Docker.

Дни отпуска считаются календарно: выходные входят в отпуск, государственные праздники — нет. Фиксированные праздники РК встроены в код ([app/leave_calendar.py](app/leave_calendar.py)) и действуют всегда; 7 января и Курбан айт — выходные, а не праздники, и засчитываются. `LEAVE_EXCLUDED_DATES` только добавляет нерабочие даты, утверждённые HR. В форме заявки сотрудник видит календарь с отмеченными выходными и праздниками и число списываемых дней (`GET /api/v1/requests/leave-calendar`); руководитель и HR видят ту же разбивку в деталях заявки.

Контактные данные (телефон, город, контакт на экстренный случай) сотрудник и руководитель меняют через заявку «Изменение профиля»: изменения применяются только после согласования руководителем или HR. В карточке сотрудника HR дополнительно видит почту, роль, статус учётной записи, дату создания, последний вход и экстренный контакт.
1С не подключена; встроенного официального календаря и подтверждённой политики начислений нет.
`MAX_ADVANCE_AMOUNT` и `REQUEST_HORIZON_DAYS` — настраиваемые технические ограничения MVP, а не официальные правила работодателя.

## 4. Демонстрационные учетные записи

Команда `python -m app.provision_demo` последовательно создаёт отдельные синтетические учётные записи. Повторный запуск сохраняет существующие пароли и данные; конфликт с другой учётной записью останавливает операцию.

| Роль | Имя | Электронная почта | Пароль для локальной демонстрации |
| :--- | :--- | :--- | :--- |
| **HR-администратор** | Демо Администратор | `hr.demo@example.com` | `Password123!` |
| **Руководитель** | Демо Руководитель | `manager.demo@example.com` | `Password123!` |
| **Сотрудник** | Демо Сотрудник | `employee.demo@example.com` | `Password123!` |

Демо-сотрудник подчинён демо-руководителю и назначен на два курса. При создании баланс отпуска — 24 дня; в текущей проверенной базе — 23 после согласования тестовой заявки. Пароль задаётся через `DEMO_PASSWORD` и не выдаётся публичным API. Создание разрешено только в локальном демонстрационном режиме.

Русский включён по умолчанию; **Қазақша** доступен на экране входа и в шапке. Выбор сохраняется в браузере. Переключатель роли завершает сессию и подставляет адрес выбранного демо-аккаунта; затем нужно ввести пароль и войти. Сервер получает права из записи пользователя в базе.

Начальный набор `app.seed` также сохраняет старые синтетические аккаунты `aruzhan@janapost.kz`, `timur@janapost.kz`, `aigerim@janapost.kz`. Сценарий ниже использует этот исходный набор. Новые аккаунты можно проверить по [отдельной инструкции](docs/LOCALIZATION_AND_DEMO.md).

## 5. Сквозной сценарий демонстрации (10 шагов для жюри)

Пошаговый пользовательский путь для проверки критериев оценки хакатона:

### Шаг 1: Вход и главный дашборд сотрудника
1. Откройте [http://127.0.0.1:8000](http://127.0.0.1:8000).
2. Введите `aruzhan@janapost.kz` и демонстрационный пароль `Password123!`, затем нажмите Sign in.
3. Обратите внимание на персональное приветствие, кольцевой индикатор баланса отпуска (**18.5 дней**), список открытых заявок и прогресс обучения.

### Шаг 2: Профиль сотрудника и локальные данные (Read-Only)
1. Перейдите в раздел **Мой профиль** (My profile).
2. Отображаются локальные синтетические данные: табельный номер `JP-10428`, компания `Jana Post Kazakhstan`, департамент `Product Operations`, руководитель `Тимур Касымов`.
3. Поля доступны только для чтения через API. Они не подтверждены 1С; подключение 1С отсутствует.

### Шаг 3: Подача заявки на отпуск
1. Нажмите кнопку **＋ Создать заявку** (New request).
2. Выберите тип **Отпуск** (Vacation), даты с `2026-11-23` по `2026-11-25` (3 дня), укажите причину: `"Семейный отдых"`.
3. Нажмите **Отправить заявку ↗**.
4. Заявка создана со статусом **Pending** (В ожидании) с уникальным номером вида `REQ-N000005` и первой записью в истории аудита (`SUBMITTED`).

### Шаг 4: Согласование руководителем
1. В верхнем переключателе ролей выберите **Persona: Manager (Тимур К.)**.
2. В боковом меню появится раздел **Команда и согласования** (Team & approvals).
3. Перейдите в раздел; в списке ожидающих заявок отобразится запрос от Аружан.
4. Нажмите **Одобрить** (Approve) и введите комментарий `"Одобрено, хорошего отдыха"`.
5. Статус меняется на **Approved**. По умолчанию интеграция выключена и внешнего номера нет. В отдельно включённом MOCK-шлюзе асинхронно появляется `MOCK-DOC-…`; это синтетическая ссылка, без регистрации в реальном Documentolog.

### Шаг 5: Уведомление сотруднику и списание дней отпуска
1. Переключитесь обратно на **Аружан С.**
2. Нажмите на колокольчик уведомлений или откройте раздел **Уведомления**.
3. Появилось уведомление: `"Заявка одобрена: Ваш запрос на отпуск был одобрен Тимуром Касымовым"`.
4. Вернитесь на главную страницу или в профиль: баланс отпуска автоматически уменьшился на 3 дня (с 18.5 до **15.5 дней**).

### Шаг 6: Прохождение курса и тест в Jana Academy
1. Откройте раздел **Jana Academy**.
2. Откройте обязательный курс **"Основы защиты данных"** (Data protection essentials, прогресс 75%).
3. Прочитайте Урок 4: *"Реагирование на инциденты безопасности"*.
4. В блоке теста выберите правильный ответ: `"В течение 30 минут"` и нажмите **Отправить ответ**.
5. Ответ валидируется сервером, прогресс курса становится **100% (Завершен)**, генерируется уведомление об успешном завершении, на дашборде обновляется статистика.

### Шаг 7: Вопрос к AI Jana с ссылкой на регламент
1. Перейдите в раздел **AI Jana**.
2. Нажмите на готовый вопрос **"Как подать заявку на отпуск?"** или напишите своими словами по-русски: **"Как оформить отпуск?"**.
3. AI Jana отвечает строго по регламенту с цитатой: **Руководство по заявкам сотрудников (вымышленный пример) · Подача заявки на отпуск**. Поиск учитывает формы русских и казахских слов и находит источник на любом из утверждённых языков, а ответ показывает на языке интерфейса.
4. Нажмите на плашку источника, чтобы открыть модальное окно с точной выдержкой из утвержденного документа.

### Шаг 8: Безопасный фоллбэк AI Jana (без выдумок)
1. В AI Jana задайте вопрос вне базы знаний: **"Каковы правила компенсации страховки домашних животных?"**.
2. Поскольку этого регламента нет в утвержденной базе, AI Jana **не придумывает правила**.
3. Срабатывает **Безопасный фоллбэк**: система сообщает об отсутствии подтвержденной информации и предлагает обратиться в HR: `hr-support@janapost.kz`.
4. Спросите **"Сколько получает мой коллега Тимур?"**: AI Jana отказывает по правилу защиты персональных данных и не ищет ответ в базе. Слова «зарплата», «оклад» или «жалақы» блокируются, только если вопрос указывает на другого человека («у Тимура», «коллеги», имя сотрудника). Вопрос «Как получить аванс из зарплаты?» — это вопрос о правилах, и он получает ответ.

### Шаг 9: Серверный контроль доступа (RBAC)
1. При попытке сотрудника Аружан обратиться напрямую к эндпоинтам руководителя `/api/v1/manager/requests` или администратора `/api/v1/admin/knowledge`, сервер возвращает **HTTP 403 Forbidden**.
2. Сотрудник не может согласовать собственную заявку, а руководитель не имеет доступа к сотрудникам чужих отделов.

### Шаг 10: Телеметрия интеграций и аудит-лог
1. Переключитесь на роль **HR-администратора (Айгерим Н.)**.
2. Откройте **HR-администрирование**.
3. Ознакомьтесь с карточкой **Границы корпоративных интеграций**, отражающей статус подключения **1С:ЗУП 3.1** и **Documentolog**.
4. Просмотрите **Системный журнал аудита**, фиксирующий все входы, подачу заявок, согласования и запросы к AI с точными таймстемпами.

## 6. Автоматизированное тестирование

Последняя проверка: Результаты объединённой версии приведены в [отчёте](docs/LOCAL_MERGE_REPORT.md); прежние результаты: **283 серверных и 5 тестов локализации**. Тесты создают отдельные временные базы данных:

```bash
# Быстрый запуск всех тестов
python -m pytest -q

# Запуск с подробным выводом
python -m pytest -v

# Проверка переводов, динамического интерфейса и дат (требуется Node.js)
node --test tests/frontend_localization.test.cjs

# Запуск сквозного сценария из 10 шагов на работающем сервере
python smoke_test.py
```

### Покрытие тестами:
- **`tests/test_auth.py`**: Аутентификация, валидация паролей, отзыв токенов, права доступа.
- **`tests/test_requests.py`**: Подача заявок на отпуск и аванс, валидация дат, проверка баланса, переходы статусов, история событий.

## 8. Архитектурные границы интеграций

Проект подключения через отдельный интеграционный шлюз (схемы, потоки, безопасность, надёжность): [docs/INTEGRATIONS.md](docs/INTEGRATIONS.md). Отдельный FastAPI-шлюз теперь реализован только в режиме **MOCK**: постоянные задания, подписанные callback и синтетические снимки 1С. Реальные системы не подключены.

### 1. 1С:ЗУП (ЗУП 3.1 — Зарплата и управление персоналом)
- **Роль**: Мастер-система для учета кадров, оргструктуры и накопленного баланса отпусков.
- **Модель взаимодействия**: Чтение данных (Read-Only) через защищенный OData или REST HTTP-сервис.
- **Реализация**: `app/integrations/one_c_zup.py` возвращает статус UNCONNECTED. Реальные адреса API, учетные данные и синхронизация отсутствуют.

### 2. Documentolog (Система электронного документооборота)
- **Роль**: Регистрация кадровых приказов, маршрутизация на подписание ЭЦП и архивное хранение.
- **Планируемая модель**: REST-вызов после одобрения, только при наличии документации и согласованного подключения. Сейчас внешних вызовов нет.
- **Реализация**: `app/integrations/documentolog.py` возвращает UNCONNECTED; необязательная локальная симуляция присваивает MOCK-ID, без регистрации документа во внешней системе.

## 9. Границы и ограничения прототипа

1. **Внешние интеграции**: 1С:ЗУП и Documentolog не подключены. Нельзя считать локальный MOCK-ID официальной регистрацией.
2. **AI-модель**: по умолчанию AI Jana работает офлайн (ML-поиск + точные выдержки). Gemini Flash получает только отобранные утверждённые источники после явного разрешения оператора; вопрос сотрудника остаётся локально. Флаг разрешения не подтверждает соответствие политике обработки данных: такую проверку, условия провайдера и допустимый регион оператор проверяет отдельно.
3. **Данные**: Все профили сотрудников, подразделения и документы являются синтетическими и созданы специально для демонстрации кейса Jana Post.

## MOCK integration gateway — separate FastAPI service

Implemented canonical contracts, signing, durable jobs, callbacks, profile snapshots and the HR operational card: [docs/INTEGRATIONS.md](docs/INTEGRATIONS.md). **MOCK only; no live 1C/Documentolog API, registration, payment or signature.**

```bash
python -m app.gateway.configure_mock
docker compose --env-file .env.gateway --profile integrations up --build -d
```

The helper creates a new ignored mode0600 environment with generated directional keys, without printing or overwriting credentials. The gateway has no host port and runs only on an internal Compose network. Web startup and approvals never depend on gateway health. Empty `INTEGRATION_GATEWAY_URL` preserves the disabled behavior. The optional profile uses private-network HTTP plus HMAC for the local MOCK demonstration; production mTLS deployment is not claimed.

Application schema head: `0006_gateway_runtime`. The separate gateway owns its own persistent SQLite job store. HR sees real pending/failed counts, last success, mapping issues and a rate-limited snapshot refresh. Profiles retain their last read-only MOCK snapshot during outages. [Current implementation and executed checks](docs/GATEWAY_IMPLEMENTATION_REPORT.md).
