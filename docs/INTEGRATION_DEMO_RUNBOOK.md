# Повторяемое локальное демо MOCK-интеграции

Сценарий проходит существующий путь JanaМен: приложение → outbox → частный шлюз → синтетический Documentolog → подписанный callback и сверка. Аккаунт вендора не нужен. Все снимки сотрудников и регистрации — MOCK. Хранилища приложения и шлюза разделены; браузер обращается только к приложению.

## Создание изолированного окружения

Из корня репозитория, при запущенном Docker Desktop и установленном окружении Python, выберите свободные порты на `127.0.0.1` и задайте `DEMO_WEB_PORT` и `DEMO_POSTGRES_PORT`:

```sh
.venv/bin/python -m app.gateway.configure_mock \
  --output .env.gateway \
  --web-port "${DEMO_WEB_PORT:?Укажите свободный порт приложения}" \
  --postgres-port "${DEMO_POSTGRES_PORT:?Укажите свободный порт PostgreSQL}"
docker compose --env-file .env.gateway --profile integrations up --build --wait --wait-timeout 180
```

Сгенерированное `COMPOSE_PROJECT_NAME=janamen-mock-<случайный>` получает собственные тома и контейнеры и не использует существующий проект Compose. Для явного имени передайте `--project-name janamen-mock-ваше-демо`. Никогда не указывайте существующий рабочий проект. Генератор отказывается перезаписывать файлы, принимать неверные имена проектов и порты и работать с `ENVIRONMENT=production`; существующие учётные данные он не меняет.

Файл `.env.gateway` исключён из Git и из контекста сборки Docker. Он создаётся с правами 0600, случайными паролями базы и демо-аккаунтов и независимыми ключами подписи. Храните его закрыто и используйте повторно для этого демо. Пароль демо-аккаунтов смотрите в своём редакторе; не вставляйте учётные данные в чат, на скриншоты и в отчёты. Внешний AI выключен. С новым окружением не используйте старый предсказуемый пароль из репозитория.

После успешного запуска и проверок здоровья откройте приложение на `127.0.0.1` и порту `WEB_PORT`. Это локальное развёртывание для разработки с HTTP во внутренней сети Compose, а не подтверждение TLS/mTLS в продакшене. У шлюза нет порта на хосте; порты приложения и PostgreSQL открыты только на loopback. Шлюз при запуске обновляет схему до v3; последняя миграция приложения — `0011_merge_profile_updates`.

## Синтетические учётные записи

Сценарий регистрации создаёт эти связанные демо-аккаунты через `app.provision_demo` и отказывается перезаписывать конфликтующие аккаунты или линии подчинения:

| Роль | Логин | Табельный номер | Доступ |
|---|---|---|---|
| Сотрудник | `employee.demo@example.com` | `DEMO-EMP-001` | Свои заявки, профиль, уведомления |
| Руководитель | `manager.demo@example.com` | `DEMO-MGR-001` | Сотрудник выше |
| HR | `hr.demo@example.com` | `DEMO-HR-001` | Очереди интеграции, обновление, сопоставление и восстановление |

Базовые синтетические аккаунты из начального наполнения: `aruzhan@janapost.kz` (`JP-10428`), `timur@janapost.kz` (`JP-10201`) и `aigerim@janapost.kz`; для них действует пароль сгенерированного окружения. В демо-режиме на экране входа можно войти одной кнопкой роли — тогда используются демо-аккаунты из таблицы. Реальные учётные записи сотрудников не создаются.

## Регистрация и повтор

```sh
docker compose --env-file .env.gateway exec -T web \
  python -m app.integrations.demo_smoke --scenario happy
docker compose --env-file .env.gateway exec -T web \
  python -m app.integrations.demo_smoke --scenario happy
```

Команда работает с реальными сессиями сотрудника, руководителя и HR в приложении на loopback. Она находит свободную будущую дату без праздников, создаёт стабильный ключ отправки, отправляет заявку дважды, одобряет один раз и ждёт MOCK-регистрации. Проверяются: тот же ID заявки, ожидаемое списание дней, отдельные статусы «Одобрено» и `REGISTERED`, MOCK-номер, ровно одно уведомление о регистрации и отказ в привилегированных действиях. В конце сессии закрываются. Повторный запуск использует сохранённые дату и ключ и проверяет, что второго списания нет. Команда никогда не удаляет заявки, не сбрасывает базу и не вызывает реального вендора.

Ожидаемый результат (номера будут другими):

```text
{'scenario': 'happy', 'request_code': 'REQ-N000021', 'business_status': 'Approved', 'integration_status': 'REGISTERED', 'external_ref': 'MOCK-DOC-…', 'reused_request': False}
{'scenario': 'happy', 'request_code': 'REQ-N000021', 'business_status': 'Approved', 'integration_status': 'REGISTERED', 'external_ref': 'MOCK-DOC-…', 'reused_request': True}
```

Для проверки повторов и перезапуска используйте тот же сценарий. Другое имя сценария намеренно создаёт ещё одну синтетическую заявку. Конфликт с существующими данными или нехватка дней отпуска приводят к понятной ошибке — используйте новый изолированный проект вместо очистки записей.

**Демонстрация в браузере.** Войдите по очереди в трёх ролях: сотрудник подаёт заявку, руководитель одобряет её (в том числе прямо из уведомления), затем откройте карточку заявки у сотрудника и карточку интеграций у HR. Покажите, что статус «Одобрено» и шаг «Регистрация» с MOCK-номером — это разные вещи. Переключение роли в интерфейсе — только удобство показа: сервер всё равно отказывает сотруднику в привилегированных маршрутах.

## Сбой шлюза и восстановление

```sh
docker compose --env-file .env.gateway stop gateway
docker compose --env-file .env.gateway exec -T web \
  python -m app.integrations.demo_smoke --scenario outage --expect-pending
docker compose --env-file .env.gateway start gateway
docker compose --env-file .env.gateway exec -T web \
  python -m app.integrations.demo_smoke --scenario outage
```

Пока шлюз остановлен, одобрение сохраняется, а профиль загружается из локального хранилища: у сотрудника статус «Одобрено», регистрация ожидает (`PENDING`, в карточке заявки — «Ожидает MOCK-шлюз»). После запуска шлюза надёжный обработчик повторяет задание с тем же ключом; команда ждёт до 90 секунд. Итог — один номер и одно уведомление без повторного списания дней. Если попытки уже исчерпаны, загляните в очередь ошибок у HR и выполните проверяемое восстановление с указанием причины. Не меняйте тело и ключ и не удаляйте принятые задания, чтобы «добиться» результата. Пропавшие из хранилища шлюза известные принятые задания требуют расследования и восстановления, а не слепой повторной отправки.

## Безопасность и проверки

```sh
.venv/bin/python -m pytest tests/test_gateway_service.py tests/test_integration_hardening.py -q
.venv/bin/python -m pytest tests/test_outbox_processes.py -q
```

Вторая команда требует `TEST_DATABASE_URL`, указывающий на заведомо одноразовую базу PostgreSQL; без неё два теста пропускаются. Каждый тест создаёт свою случайную схему и удаляет только её. Никогда не указывайте рабочую или пользовательскую базу. Полный набор тестов покрывает также права на восстановление, сопоставление, предварительную проверку миграций, смену ключей, подпись тела и параметров, хранение nonce, откат при сбое callback и неверные области доступа сотрудника и руководителя.

Бизнес-запросы к шлюзу ограничены постоянной поминутной квотой на ключ `GATEWAY_REQUESTS_PER_MINUTE` (по умолчанию 600). Подписанный `GET /health` имеет отдельную квоту `GATEWAY_HEALTH_REQUESTS_PER_MINUTE` (по умолчанию 60), поэтому мониторинг не расходует бизнес-ёмкость. Обе квоты подписаны, защищены от повторов и ограничены; другой метод или маршрут не может воспользоваться квотой `/health`. Ответ `429` содержит `Retry-After`, неверная подпись — 401. Задайте подходящие лимиты, сохраняйте частную сеть и следите за логами отказов. Фиксированное окно не заменяет защиту на границе сети.

## Сохранение и остановка

```sh
docker compose --env-file .env.gateway --profile integrations stop
```

Это сохраняет сгенерированное окружение и оба хранилища для следующего запуска. Не используйте удаление томов, prune, удаление строк или замену учётных данных как способ «повторить» сценарий. Перед плановым обновлением сделайте резервную копию хранилища шлюза по [регламенту восстановления](RECOVERY_AND_OPERATIONS.md).

## Условие для реального вендора

Демо-аккаунт Documentolog или 1С станет полезен только после получения от партнёра утверждённых контрактов API, доступа к синтетической песочнице, сервисных прав, способа проверки авторизации и webhook, сопоставления полей и отпусков и сетевых требований TLS. Обычный логин вендора этих контрактов не даёт. Запись в 1С, подписание в Documentolog и безопасность продакшена остаются не проверенными; ни один коннектор не показывает статус CONNECTED.
