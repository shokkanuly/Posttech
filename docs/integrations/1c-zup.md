# Адаптер 1С:ЗУП — спецификация

> Статус: в коде работает **только MOCK-режим** (синтетические снимки сотрудников через внутренний шлюз). Реальная 1С не подключена. Этот документ описывает, как подключать её после согласования с администратором 1С Jana Post.

## 1. Назначение и граница уверенности

Что должен делать адаптер:

- Читать согласованные для JanaМен эталонные поля сотрудника и оргструктуры.
- Читать остатки отпуска и дату, на которую они рассчитаны, — если конфигурация 1С отдаёт нужный расчёт.
- На отдельном, отдельно согласованном этапе — передавать полностью согласованную кадровую операцию или получать официальную запись/ссылку после обработки в 1С. **Только если это поддерживают реальная конфигурация и бизнес-процесс.**

**Неизвестно на этапе проектирования:** тип развёртывания (облако или свои серверы), версия продукта и платформы, точная конфигурация и локализация, опубликованные сервисы, доступные объекты OData, собственные HTTP-сервисы, способ авторизации, сетевой доступ, ключи сотрудников, источник остатка отпуска, логика согласования и проведения. Этот документ не доказывает, что какой-либо конкретный endpoint 1С существует.

## 2. Варианты интеграции, которые нужно выяснить

1С:Предприятие умеет отдавать стандартный REST-интерфейс OData (версия 3), если прикладное решение опубликовано и объекты в нём открыты. Что именно доступно, зависит от реальной информационной базы. Официальные материалы:

- Обзор REST-интерфейса: <https://kb.1ci.com/1C_Enterprise_Platform/1C_Enterprise_Platform_Overview/Integration/REST_interface/>
- Публикация стандартного REST API для информационной базы: <https://kb.1ci.com/1C_Enterprise_Platform/FAQ/Development/Integration/Publishing_standard_REST_API_for_your_infobase/?language=en>

Возможные варианты в порядке предпочтения (после выяснения деталей):

1. Специальный HTTP-сервис, согласованный с заказчиком или вендором, со стабильными бизнес-операциями: сотрудники, остаток отпуска, передача отпуска.
2. Опубликованные объекты OData — только для явно согласованного чтения и только если их смысл совпадает с нужным контрактом.
3. Собственное расширение или сервис на стороне 1С — если текущие метаданные не открывают нужные данные безопасно или официальная операция должна создаваться через бизнес-логику.

Нельзя выполнять универсальные операции создания и изменения над произвольными объектами метаданных 1С вместо понимания кадровой логики. Для проведения документов, начисления отпуска и расчёта остатков используется поддерживаемая бизнес-операция, а не догадки о низкоуровневых записях.

## 3. Внутренний интерфейс адаптера

Бизнес-логика работает с внутренним нормализованным интерфейсом, а не с названиями endpoint-ов 1С. Пример протокола на Python:

```python
from datetime import datetime, date
from decimal import Decimal
from typing import Protocol, Sequence

class HRAdapter(Protocol):
    async def get_employee(self, external_employee_id: str) -> "EmployeeRecord | None": ...
    async def list_employees_changed_since(
        self, cursor: str | None, limit: int = 500
    ) -> "EmployeePage": ...
    async def get_leave_balance(
        self, external_employee_id: str, leave_type: str, as_of: date | None = None
    ) -> "LeaveBalance": ...
    async def submit_approved_leave(
        self, command: "ApprovedLeaveHandoff", idempotency_key: str
    ) -> "HRTransactionResult": ...
    async def get_transaction_status(
        self, external_reference: str
    ) -> "HRTransactionResult": ...
```

Реальный адаптер реализует только возможности, подтверждённые реальным контрактом. Неподдерживаемые операции явно возвращают ошибку (например, `CapabilityNotConfigured`), а не делают вид, что всё прошло успешно. В MOCK-режиме поддерживаемый интерфейс работает детерминированно.

### Внутренние объекты данных

`EmployeeRecord` — запись сотрудника:

- `external_id: str` — стабильная ссылка на сотрудника из объекта или сервиса 1С.
- `employee_number: str | None` — табельный номер.
- `full_name: str` — ФИО.
- `department_external_id: str | None`, `department_name: str | None` — подразделение.
- `job_title: str | None` — должность.
- `manager_external_id: str | None` — руководитель.
- `employment_status` — статус занятости по согласованному справочнику.
- `email: str | None` — только если согласовано для приложения.
- `effective_at: datetime | None`, `source_updated_at: datetime | None`, `source_version: str | None` — даты действия и версия источника.

`EmployeePage` — страница выгрузки:

- `items: list[EmployeeRecord]`
- `next_cursor: str | None`
- `is_complete_snapshot: bool` — `true` только если контракт сервиса прямо говорит, что это полный снимок.

`LeaveBalance` — остаток отпуска:

- `employee_external_id: str`
- `leave_type: str` — нормализован по подтверждённому справочнику.
- `available_days: Decimal` — доступные дни.
- `as_of: datetime | date` — на какую дату рассчитан.
- `period_start: date | None`, `period_end: date | None` — рабочий период.
- `source_version: str | None`, `retrieved_at: datetime` — версия и время получения.

`ApprovedLeaveHandoff` — передача согласованного отпуска:

- `janamen_request_id: UUID`, `employee_external_id: str`
- `start_date: date`, `end_date: date`, `leave_type: str`
- `approved_by_external_id: str | None`, `approval_timestamp: datetime`
- `documentolog_document_id: str | None`
- `correlation_id: UUID`

Это внутренняя команда, **а не утверждение о названиях полей в 1С**. Реальный адаптер сопоставляет её с 1С только после того, как администратор 1С подтвердит объект, поля, порядок операции и правила проверки.

`HRTransactionResult` — результат операции:

- `state` — одно из `PENDING`, `ACCEPTED`, `COMPLETED`, `REJECTED`, `UNKNOWN`, `UNSUPPORTED`.
- `external_reference: str | None` — внешняя ссылка.
- `message_code: str | None`, `safe_message: str | None` — код и безопасный текст сообщения.
- `confirmed_at: datetime | None`
- `raw_status_code: str | None` — необязательный, очищенный от лишних данных код провайдера.

## 4. Потоки данных

### 1С → JanaМен: синхронизация сотрудников

1. Фоновый процесс вызывает адаптер с `cursor` и размером страницы.
2. Адаптер приводит ответ провайдера к `EmployeeRecord`.
3. Сервис синхронизации проверяет обязательные поля и значения справочников.
4. Внутренний сотрудник находится по существующему стабильному сопоставлению ID. **Сопоставление по имени запрещено.**
5. Эталонные поля обновляются в транзакции, сохраняется `source_updated_at`; курсор синхронизации сдвигается только после фиксации страницы.
6. Неизвестные или неоднозначные записи уходят в карантин (очередь проверки HR), а не привязываются к случайной учётной записи.
7. Если в инкрементальном ответе сотрудника нет, он сохраняется. Неактивным он помечается только по явному статусу или признаку удаления из эталонного источника либо после проверенной сверки полного снимка.

### 1С → JanaМен: остаток отпуска

- Запрашивается по требованию или с коротким настраиваемым кэшем; нельзя ходить в 1С при отрисовке каждого блока на главной.
- Хранится как `Decimal` вместе с типом отпуска, периодом, `as_of`, временем получения и версией источника.
- Различаются состояния `FRESH` (свежий), `STALE` (устарел), `UNAVAILABLE` (недоступен) и `NOT_FOUND` (не найден). Отсутствие ответа — это не ноль дней.
- Порог устаревания задаётся настройкой или бизнес-требованиями. До их согласования интерфейс показывает время снимка и не обещает данные «в реальном времени».
- Эталоном является 1С: показанное в интерфейсе или закэшированное значение не резервирует отпуск в 1С.

### JanaМен → 1С: официальная операция (будущий этап)

Запись в 1С по умолчанию выключена. Перед включением нужны:

- проверенные объект или сервис и схема данных;
- задокументированные права сервисной учётной записи;
- официальное сопоставление полей и смысл дат и типов отпуска;
- описанный процесс проверки и проведения (нужно ли проводить документ и кто это делает);
- стабильная идемпотентность или способ выявлять дубли на стороне 1С;
- тесты в песочнице, подтверждающие операцию и способ узнать её результат;
- одобрение ответственного сотрудника HR.

Согласование руководителем или подпись в Documentolog **не означают** автоматически, что кадровая операция в 1С выполнена.

## 5. HTTP, авторизация и повторы

Транспорт может быть OData или собственным сервисом; он изолируется в отдельном модуле реального адаптера и в настройках. Используется HTTPX с таймаутами, проверкой TLS, ограниченным пулом соединений и маскированием секретов в логах. Авторизация может быть базовой (сервисная учётная запись), через веб-сервер или SSO либо через отдельный сервисный ключ — это выясняется у администратора 1С, угадывать нельзя.

Минимальный набор нормализованных ошибок:

- `AUTH_FAILED` — 401/403 или аналог провайдера.
- `VALIDATION_FAILED` — неверный запрос, поле или бизнес-правило; автоматически не повторяется.
- `NOT_FOUND` — сопоставленный сотрудник или операция не существует.
- `RATE_LIMITED` — 429 или явное ограничение провайдера; учитывается `Retry-After`.
- `TIMEOUT` — ответ не получен; чтение обычно можно повторить, у записи результат может быть неизвестен.
- `PROVIDER_UNAVAILABLE` — временная ошибка 5xx или сети.
- `CONFLICT` — устаревшая версия, дубль или конфликт бизнес-состояния.
- `UNKNOWN_OUTCOME` — запись, возможно, прошла, но ответ потерян; перед повторной отправкой нужна сверка.

Ошибки проверки и авторизации (4xx) по умолчанию не повторяются. Для таймаутов и 5xx при чтении — ограниченные повторы с экспоненциальной задержкой и случайным разбросом. При таймауте записи результат ищется по внешней ссылке или ключу корреляции, если это поддерживается; иначе — ручная сверка, а не слепая повторная отправка.

В развёрнутых средах секреты передаются через менеджер секретов или защищённые переменные окружения. Названия — предлагаемое соглашение, а не требование 1С. Реальные значения не задаются, пока не закрыты открытые вопросы.

## 7. Чек-лист вопросов к администратору 1С

- Полное название продукта и конфигурации (1С:ЗУП для Казахстана или другая локализация), релиз и версия платформы.
- Тип развёртывания, сетевой маршрут, VPN и ограничения по IP, TLS и цепочка сертификатов.
- Опубликован ли OData; базовый адрес; доступные метаданные; список разрешённых сущностей и свойств; разрешённые методы.
- Если есть собственный HTTP-сервис — его OpenAPI или контракт и порядок выпуска изменений.
- Схема авторизации, сервисная учётная запись, минимальные роли, порядок смены учётных данных.
- Стабильный ключ сотрудника и правила уникальности табельного номера.
- Смысл подразделения и руководителя, значения статуса занятости.
- Точный источник остатка отпуска, период начисления, округление, учёт согласованных отпусков, типы отпусков, допустимое устаревание.
- Официальный формат передачи отпуска, требования к проведению, внешняя идемпотентность, официальная ссылка и запрос статуса.
- Лимиты запросов и пакетов, окна обслуживания, требования к аудиту, тестовые данные и контакты.

Пока на эти вопросы нет ответов, поддерживается только MOCK-режим.

## 8. Что уже реализовано в JanaМен

- **Приём подписанных MOCK-снимков** сотрудников по табельному номеру (`app/integrations/profile_sync.py`, источник снимков — внутренний шлюз `app/gateway/`). Обновляются только существующие профили; сохраняются источник, дата снимка и состояние синхронизации.
- **Устойчивость к сбоям:** при недоступности шлюза профиль показывает последний сохранённый снимок.
- **Очередь проверки HR:** неизвестные табельные номера и конфликты остатков попадают в очередь; HR вручную задаёт соответствие с указанием причины (`app/integrations/recovery.py`, карточка «Границы корпоративных интеграций» на странице HR-админа).
- **Не реализовано и выключено:** реальный коннектор 1С, проверенные адреса и авторизация, запись в 1С.

При подключении реального адаптера нужно расширять эту границу снимков, а не создавать параллельные таблицы профиля и отдельную синхронизацию. Сопоставление — только по стабильному табельному номеру, автоматическое создание учётных записей запрещено.
