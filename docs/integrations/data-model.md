# Модель данных, идентификаторы и сопоставление полей

> Это целевая модель для подключения реальных 1С:ЗУП и Documentolog. Перед добавлением таблиц сверяйтесь с текущими моделями (`app/models/`) и миграциями (`migrations/`, сейчас последняя — `0011_merge_profile_updates`): многие сущности уже есть, дублировать их нельзя.

## 1. Правила идентификации

- У каждого сотрудника JanaМен есть внутренний неизменяемый `employee_id`.
- Ссылка на сотрудника во внешней системе хранится отдельно, с указанием системы и конфигурации. Табельный номер не считается глобально уникальным, пока владелец данных не подтвердит границы его уникальности.
- Записи **никогда** не сопоставляются только по ФИО, транслитерации, e-mail или подразделению. Эти поля — лишь подсказка для ручной проверки, а не автоматическое сопоставление.
- Ведётся стабильная таблица сопоставлений; создание и изменение сопоставления записывается в аудит.

## 2. Предлагаемые таблицы

Адаптируются под текущие соглашения ORM и базы. Если равноценные таблицы уже есть, параллельные схемы не создаются.

### `employees` — сотрудники

- `id UUID PRIMARY KEY`
- `employee_number TEXT NULL` — табельный номер
- `full_name TEXT NOT NULL`
- `department_id UUID NULL`, `manager_employee_id UUID NULL`, `job_title TEXT NULL`
- `employment_status TEXT NOT NULL`
- `email TEXT NULL` — только если согласовано
- `source_provider TEXT NOT NULL`
- `source_updated_at TIMESTAMPTZ NULL`, `last_synced_at TIMESTAMPTZ NULL`
- `record_freshness TEXT NOT NULL` — `FRESH`, `STALE`, `UNAVAILABLE`, `UNKNOWN`
- `created_at`, `updated_at`

Учётная запись для входа хранится отдельно, если у неё другой жизненный цикл и права. Импорт строки из 1С сам по себе не даёт доступа к входу.

### `external_id_mappings` — сопоставления с внешними системами

- `id UUID PRIMARY KEY`
- `provider TEXT NOT NULL` — `onec`, `documentolog`
- `entity_type TEXT NOT NULL` — `employee`, `department`, `document`, `hr_transaction`
- `internal_id UUID NOT NULL`, `external_id TEXT NOT NULL`
- `source_key_type TEXT NULL` — что именно означает ID
- `created_at TIMESTAMPTZ NOT NULL`, `last_verified_at TIMESTAMPTZ NULL`
- `metadata JSONB NOT NULL DEFAULT '{}'`

Ограничения: уникальность `(provider, entity_type, external_id)`, а там, где задумана связь один к одному, — `(provider, entity_type, internal_id)`. Если несколько внешних ссылок на одну сущность допустимы, это моделируется явно, а не снятием ограничений.

### `leave_balances` — остатки отпуска

- `id UUID PRIMARY KEY`, `employee_id UUID NOT NULL`
- `leave_type TEXT NOT NULL`
- `available_days NUMERIC(8,2) NOT NULL`
- `period_start DATE NULL`, `period_end DATE NULL`
- `as_of TIMESTAMPTZ NOT NULL`, `retrieved_at TIMESTAMPTZ NOT NULL`
- `source_provider TEXT NOT NULL`, `source_version TEXT NULL`
- `freshness TEXT NOT NULL`
- уникальность и индексы — по сотруднику, типу отпуска и правилам периода, согласованным с HR.

Пропущенное значение не превращается в `0`: отсутствующий или устаревший остаток — отдельное состояние.

### `requests` — заявки

- `id UUID PRIMARY KEY`, `request_number TEXT UNIQUE`
- `request_type TEXT NOT NULL` (например, `VACATION`)
- `employee_id UUID NOT NULL`, `manager_employee_id UUID NULL`
- `start_date DATE NULL`, `end_date DATE NULL`
- `reason TEXT NULL` — может содержать персональные данные; видимость и срок хранения ограничены
- `request_status`, `approval_status`, `document_status`, `hr_processing_status` — отдельные статусы
- `idempotency_key_hash TEXT NULL`, `correlation_id UUID NOT NULL`
- `version INTEGER NOT NULL DEFAULT 1`
- даты и ID инициаторов

Исходный ключ идемпотентности без необходимости не хранится — только хеш или отдельная таблица ключей.

### `request_events` — события заявки (только добавление)

- `id UUID PRIMARY KEY`, `request_id UUID NOT NULL`
- `event_type TEXT NOT NULL`, `actor_type TEXT NOT NULL`, `actor_id UUID NULL`
- `from_state JSONB NULL`, `to_state JSONB NULL`, `reason_code TEXT NULL`
- `metadata JSONB NOT NULL DEFAULT '{}'` — без лишних данных, только разрешённые поля
- `occurred_at TIMESTAMPTZ NOT NULL`, `correlation_id UUID NOT NULL`

### `external_documents` — внешние документы

- `id UUID PRIMARY KEY`, `request_id UUID NOT NULL`, `provider TEXT NOT NULL`
- `external_document_id TEXT NULL`, `status TEXT NOT NULL`
- `document_url TEXT NULL`
- `download_link_metadata JSONB NULL` — без долгоживущих секретов, ссылки защищены
- `token_secret_ref TEXT NULL` — ссылка на зашифрованное хранилище, если токен действительно нужен
- `submitted_at`, `completed_at`, `last_provider_event_at`, `last_reconciled_at TIMESTAMPTZ NULL`
- `submission_payload_digest TEXT NULL`
- `created_at`, `updated_at`

Ссылки провайдера показываются пользователю только после проверки права на заявку. Bearer-токен Documentolog не хранится открытым текстом.

### `integration_jobs` — транзакционный outbox

- `id UUID PRIMARY KEY`
- `provider`, `operation`, `aggregate_type TEXT NOT NULL`, `aggregate_id UUID NOT NULL`
- `idempotency_key TEXT NOT NULL` — внутренний ключ без персональных данных
- `correlation_id UUID NOT NULL`
- `payload JSONB NOT NULL` — только минимально нужные данные, без секретов и больших файлов
- `status TEXT NOT NULL` — `PENDING`, `RUNNING`, `RETRY_WAIT`, `SUCCEEDED`, `FAILED`, `UNKNOWN_OUTCOME`, `DEAD_LETTER`
- `attempt_count INTEGER NOT NULL DEFAULT 0`, `next_attempt_at TIMESTAMPTZ NULL`
- `last_error_code TEXT NULL`, `last_error_safe_message TEXT NULL`
- `lease_until TIMESTAMPTZ NULL`
- даты

Уникальность по ключу идемпотентности и операции. Обработчик должен быть безопасен, если аренда истекла и задание выполнилось повторно.

### `integration_events` — входящие события

Метаданные приёма и дедупликации webhook: провайдер, отпечаток события, внешний ID документа, тип события, хеш тела, время получения, результат проверки, статус обработки, очищенные метаданные. Уникальность — по провайдеру и отпечатку. Если провайдер позже начнёт отдавать ID события, дубли отсекаются по нему.

### `sync_cursors` — курсоры синхронизации

Курсор по провайдеру и ресурсу, время последней успешной страницы, время последней полной сверки, статус запуска. Курсор сдвигается только после фиксации соответствующих записей.

### `audit_events` — журнал аудита

Кто, что, над чем, когда, ID корреляции и результат. Не хранятся учётные данные, полный ИИН, полный телефон, полная ссылка или токен Bearer и лишние копии документов.

## 3. Сопоставление полей

| Понятие JanaМен | Источник в 1С:ЗУП (уточнить) | Источник в Documentolog | Правила |
|---|---|---|---|
| `employee_id` | Внутренний UUID JanaМен, связанный со стабильным ключом 1С | обычно не используется | Никогда не используется как внешний ключ |
| `external_employee_id` | Стабильная ссылка на сотрудника в 1С (точное свойство неизвестно) | идентификатор получателя может быть ИИН, телефон или e-mail — это не замена ID сотрудника | Хранятся раздельно, в своих пространствах имён |
| `employee_number` | Табельный номер или код в 1С | — | Хранится строкой, с ведущими нулями |
| `full_name` | Согласованное поле 1С | имя подписанта может прийти в webhook | Отображаемое имя задаёт кадровый источник; имя из webhook не подтверждает личность |
| `department` | Ссылка или название подразделения в 1С | — | По возможности используется сопоставленный внешний ID подразделения |
| `manager` | Ссылка на руководителя в 1С или согласованное сопоставление HR | подписантом может быть руководитель, но связь задаётся явно | Права на согласование берутся из разрешённого сопоставления, а не из совпадения имён |
| `employment_status` | Статус занятости в 1С | — | Сопоставляется с внутренним справочником; неизвестные значения — в карантин с оповещением |
| `leave_balance_days` | Подтверждённая операция, отчёт или регистр остатков в 1С | — | Десятичное число; хранятся `as_of`, тип отпуска, период, свежесть |
| `janamen_request_id` | Передаётся как ключ корреляции, если операция это поддерживает | хранится локально; передаётся в метаданных, если поддерживается | UUID и ID корреляции — внутренние якоря |
| `external_document_id` | Необязательная ссылка в официальной кадровой операции | `doc_id` из webhook или проверенного ответа на создание | Никогда не выводится из URL |
| `document_status` | — | нормализованное состояние из webhook | Подписанный документ ещё не означает завершённую операцию в 1С |
| `official_hr_reference` | Ссылка на операцию в 1С (возвращается или запрашивается) | — | Заполняется только после подтверждения провайдером по контракту |

## 4. Правила для дат и чисел

- Отметки времени при передаче — ISO 8601 со смещением; моменты времени приводятся к UTC.
- Начало и конец отпуска — тип `DATE`, если контракт HR API не требует времени. Дата на весь день не превращается в метку UTC, которая может сдвинуть календарный день.
- Дни отпуска и деньги — `Decimal` / SQL `NUMERIC`, а не двоичный float.
- Время в источнике и время получения в JanaМен хранятся раздельно.
- Если провайдер не отдаёт версию или время изменения, хранится `NULL`; придумывать значение и выдавать его за эталонное нельзя.

## 5. Кто владеет полями

| Поле | Владелец | Поведение JanaМен |
|---|---|---|
| Юридические данные сотрудника и официальные кадровые поля | 1С / HR (уточнить) | Кэш только для чтения; исправляется в источнике или через утверждённый процесс HR |
| Текущий руководитель и подразделение | 1С / HR (уточнить) | Импортируются с аудитом изменений; без догадок по именам |
| Остаток отпуска | Подтверждённый расчёт в 1С | Только чтение, с отметкой свежести |
| Описание заявки и выбранные даты | JanaМен до отправки и согласования | Изменения версионируются и пишутся в аудит; ключевые поля фиксируются при передаче |
| Внутренние согласования | JanaМен или обязательный внешний процесс (уточнить) | История событий с проверкой ролей |
| Подпись и официальные подписанные файлы | Documentolog | Отражаются проверенные события провайдера; скачивание защищено |
| Официальная кадровая запись | 1С | Завершённой считается только после проверенного результата операции |

## 6. Что уже есть в текущей схеме

- Модели приложения и версионированные миграции `0001`–`0011` в `migrations/`; модели — в `app/models/`.
- Ограничения на уровне БД (`0009_domain_checks`): допустимые статусы и типы заявок, порядок дат, положительные суммы, корректные данные изменения профиля.
- Ключи повторной отправки (`0007_submission_keys`): повторный запрос с тем же `Idempotency-Key` и тем же телом возвращает ту же заявку, с другим телом — ошибку 409.
- Состояние синхронизации профилей, очередь проверки HR и outbox — модели в `app/models/integration.py`.
- У внутреннего шлюза своё хранилище заданий и собственные миграции (`app/gateway/migrate.py`), отдельно от базы приложения.
