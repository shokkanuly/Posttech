# Адаптер Documentolog Business — спецификация

> Статус: в коде работает **MOCK-регистрация** через внутренний шлюз (номер вида `MOCK-DOC-…`). Это не подключение к реальному Documentolog и не доказательство подписания. Документ описывает, как подключать реальный API после согласования с Documentolog и Jana Post.

## 1. Роль и важный побочный эффект

Documentolog отвечает за жизненный цикл внешнего электронного документа и подписи. JanaМен создаёт заявку и решает, можно ли отправлять её на подпись; Documentolog владеет номером документа, статусом подписания и возвращаемыми файлами и ссылками.

**Критично:** публичная документация Documentolog Business описывает объединённый вызов «создать документ + получить токен доступа». В ней сказано, что документ **нельзя создать черновиком**: при создании он сразу отправляется получателю. Также отправитель (`sSender`) обязан быть подписантом. Значит, реальный вызов — это видимое внешнее действие, а не безобидная «подготовка черновика». Вызывать его можно только после проверки согласования, данных подписантов и получателей, содержимого документа и окончательного разрешения на отправку. Любой альтернативный порядок нужно подтвердить у Documentolog, а не предполагать.

Официальное руководство: <https://documentolog.com/en/integrations-business/api>

## 2. Что известно об API из публичной документации

Эти сведения взяты из руководства по ссылке выше и всё равно должны быть сверены с аккаунтом и договором заказчика:

- Доступ к API открывается в кабинете Documentolog Business, раздел «Интеграции → API Documentolog»; по руководству он доступен на тарифе Business.
- Создание документа и запрос токена: `POST https://apibusiness.documentolog.com/json/external/oauth/token` с заголовком `api-key` и JSON-телом.
- В примере ответа есть `status`, `data.access_token`, `scope` и `token_type`. Токен действует 30 дней и передаётся как `Authorization: Bearer <token>`.
- Поля запроса: `aAttachments`, `sSetWebhookUrl`, `iSendToRecipient`, `mRecipient`, `mPhonesForSms`, `iRecipientSignatureRequired`, `mAvailableSignatureMethodsForRecipient`, `mAvailableSignatureMethods`, `sSender`.
- Идентификатором получателя может быть ИИН, БИН, телефон или e-mail. Используется только идентификатор и маршрут подписи, явно согласованный организацией; идентификаторы — чувствительные данные.
- Поддерживаемые форматы: doc/docx, xls/xlsx, ppt/pptx, pdf, rar/zip, rtf, TIFF, JPEG/JPG, PNG, GDoc. Имя файла до расширения — не длиннее 32 символов.
- События webhook: `document_sent`, `signer_signed`, `signer_declined`, `document_completed`. У всех одинаковый `doc_id` документа; события подписантов содержат имя подписанта и идентификатор получателя. Событие завершения может содержать ссылки на документ и скачивание (в том числе с ЭЦП).
- Повторная доставка webhook: через 5, 15, 30, 60, 120, 240, 480, 960 и 1440 минут; после этого событие помечается неуспешным и больше не отправляется.
- Ссылки в событии завершения требуют для скачивания тот же Bearer-токен. Это не публичные адреса, их нельзя отдавать в браузер без проверки прав.
- Ограничения: нет черновиков, подпись отправителя обязательна. Описан также сценарий подписи во встроенном окне (iframe) с сигналами `postMessage`.

Публичная документация **не подтверждает** наличие криптографической подписи webhook, универсального запроса статуса, заголовка идемпотентности или отдельного API состояний для заказчика. Каждый пункт нужно подтвердить у Documentolog.

## 3. Внутренний контракт адаптера

Бизнес-логика работает с внутренним нормализованным контрактом и не зависит от префиксов `s`/`i`/`m` в полях публичного API.

```python
class DocumentAdapter(Protocol):
    async def submit_document(
        self, payload: "DocumentSubmission", idempotency_key: str
    ) -> "DocumentSubmissionResult": ...

    async def get_document_status(
        self, external_document_id: str
    ) -> "DocumentStatusResult": ...

    async def verify_webhook(
        self, headers: Mapping[str, str], raw_body: bytes
    ) -> "WebhookVerificationResult": ...
```

`get_document_status` и `verify_webhook` могут быть ограничены, пока провайдер не подтвердит механизмы. Придумывать endpoint-ы и схемы подписи нельзя. Реестр возможностей помечает `webhook_signature_verification`, `status_polling`, `idempotent_create`, `document_download` как `SUPPORTED`, `UNSUPPORTED` или `NOT_CONFIRMED`.

`DocumentSubmission` — отправка документа:

- `janamen_request_id: UUID`, `correlation_id: UUID`
- `document_type: str` — по согласованному справочнику типов документов
- `title: str`
- `attachment_url: str` — короткоживущая HTTPS-ссылка, доступная провайдеру и защищённая правами
- `sender_identifier: str` — ИИН/БИН или согласованный идентификатор отправителя (чувствительные данные)
- `recipients: list[DocumentRecipient]`
- `sender_signs: bool` — для публичного сценария всегда `true`, если вендор не подтвердит иное
- `recipient_signature_required: bool`
- `recipient_signing_methods: list[str]`, `sender_signing_methods: list[str]`
- `send_now_confirmed: bool` — явное разрешение на отправку

`DocumentRecipient` — получатель:

- `recipient_identifier: str` (чувствительные данные)
- `display_name: str | None`
- `phone_for_sms: str | None` — только для согласованного сценария подписи по SMS
- `signing_required: bool`

`DocumentSubmissionResult` — результат отправки:

- `state` — `ACCEPTED`, `REJECTED`, `UNKNOWN` или `UNSUPPORTED`
- `external_document_id: str | None` — из `doc_id` провайдера
- `access_token: SecretStr | None` — не хранится в обычных JSON заявки и логах; только в зашифрованном хранилище с ограниченным доступом, если без этого нельзя продолжить сессию
- `signing_session_url: str | None` — со строгой проверкой пользователя и безопасной работой с токеном
- `safe_message: str | None`, `correlation_id: UUID`

`ExternalDocumentEvent` — внешнее событие документа:

- `provider: "documentolog"`, `external_document_id: str`
- `event_type` — `DOCUMENT_SENT`, `SIGNER_SIGNED`, `SIGNER_DECLINED`, `DOCUMENT_COMPLETED`, `UNKNOWN`
- `occurred_at: datetime | None` — только если пришло от провайдера, не придумывается
- `recipient_ref_hash: str | None` — предпочтительно хеш вместо идентификатора, без лишних персональных данных
- `document_url`, `download_url: str | None`
- `payload_digest: str` — хеш тела события

## 4. Сопоставление полей запроса (только поля из публичной документации)

| Внутреннее значение | Поле API | Примечание |
|---|---|---|
| `attachment_url` | `aAttachments: [url]` | Ссылка должна быть доступна провайдеру и безопасно отдавать согласованный документ. Уточнить авторизацию, списки разрешённых адресов и лимит размера. |
| `webhook_url` | `sSetWebhookUrl` | Публичный адрес; способ проверки подлинности webhook ещё нужно подтвердить. |
| `send_now_confirmed` | `iSendToRecipient` | Документация описывает 1 = да, 0 = нет, но черновиков нет; значение `0` нельзя считать отложенной отправкой без письменного подтверждения. |
| `recipients[].recipient_identifier` | `mRecipient` | Только типы и форматы идентификаторов из договора. |
| Данные SMS | `mPhonesForSms` | Заполняется только при явно выбранной подписи по SMS. |
| `recipient_signature_required` | `iRecipientSignatureRequired` | В формате 1/0, как ожидает провайдер. |
| Способы подписи получателя | `mAvailableSignatureMethodsForRecipient` | Примеры значений: `eds`, `egov-qr`, `adobe-sign`, `sms`. |
| Способы подписи отправителя | `mAvailableSignatureMethods` | Те же примеры значений. |
| Идентификатор отправителя | `sSender` | ИИН или БИН; отправитель обязан быть подписантом. |

Этот endpoint — создание документа с получением токена, а не просто авторизация, которую можно безопасно выполнить заранее. Токен для реального документа запрашивается только после того, как пройдены все проверки на стороне JanaМен.

## 5. Обработка webhook

Примеры из публичной документации:

```json
{"event":"document_sent","doc_id":"KZ000000000000000001234567"}
```

```json
{
  "event":"signer_signed",
  "doc_id":"KZ000000000000000001234567",
  "signer":{"name":"Example Name","recipient":"redacted-recipient"}
}
```

Событие завершения может содержать `document`, `download_all_files`, `download_files`, `download_files_with_eds` и `download_files_with_eds_ez`. Ссылки — это данные провайдера: требуется HTTPS, хост сверяется со списком разрешённых, произвольные адреса из входящих данных не открываются, а Bearer-токен прикладывается только к проверенным доменам провайдера.

**Уникальность события.** В примерах нет уникального ID события. Дубли отсекаются по отпечатку `(provider, doc_id, event, хеш получателя-подписанта, хеш тела)`, хеш исходного тела сохраняется. Обработка идемпотентна, даже если одно событие пришло несколько раз. Действия разных подписантов сохраняются все: два разных подписанта не считаются дублем только из-за одинакового типа события.

**Подлинность webhook.** Документация показывает формат событий и повторы, но не описывает заголовок криптографической подписи. Придумывать алгоритм подписи нельзя. До запуска нужен официальный способ проверки от провайдера. Если его нет, с провайдером и ответственным за безопасность согласуется компенсирующая схема (ограничение сетей-источников, секрет в адресе, если поддерживается, и сверка статуса). Сам формат JSON не подтверждает, кто отправил запрос.

## 6. Встроенное окно подписи и безопасность браузера

Документация описывает адрес встроенного окна вида `https://apibusiness.documentolog.com/external/sign/embedded?sParams=<token>` и сообщения вида `{isDocumentolog:true, type:'sign', success:true|false, signType:'eds'|'egov_gr'}`, а также `user-close` и `already-signed`.

Если это реализуется:

- Сообщение `postMessage` само по себе не доказывает юридически завершённую подпись. Проверяется `event.origin` (точный подтверждённый адрес провайдера), `event.source` и содержимое; итог подтверждается webhook-ом или проверенным серверным результатом провайдера.
- Токен окна ограничен текущей заявкой и выдаётся только пользователю, у которого есть право. Его нельзя сохранять в localStorage, аналитике и логах.
- Нужны строгие `Content-Security-Policy`/`frame-src`, `Referrer-Policy: no-referrer` и отсутствие сторонних скриптов на странице подписи.
- Токен передаётся в параметре адреса, поэтому нужно не допускать его попадания в логи доступа, браузерную аналитику, отчёты об ошибках и заголовок Referer.
- Адрес окна, формат сообщений, требования к iframe и срок жизни токена перепроверяются перед запуском.

## 7. Сопоставление статусов

События провайдера переводятся во внутренние статусы документа, но никогда не означают автоматически, что кадровый процесс завершён:

| Событие провайдера | Внутренний статус документа | Значение |
|---|---|---|
| внешнего документа ещё нет | `NOT_CREATED` | Отправка не выполнялась |
| запрос создания выполняется | `SUBMISSION_PENDING` | Задание в очереди или отправляется |
| таймаут после запроса, который мог дойти | `SUBMISSION_UNKNOWN` | Перед повторной отправкой нужна сверка |
| `document_sent` | `SENT` | Провайдер отправил документ получателю |
| `signer_signed` | `PARTIALLY_SIGNED` | Один подписант подписал; могут остаться другие |
| `signer_declined` | `DECLINED` | Подписант отказал; нужно решение HR или оператора |
| `document_completed` | `SIGNED` | Все стороны подписали |
| ошибка проверки или прав | `FAILED` | Известная ошибка; повтор только после исправления |
| ручная отмена по утверждённым правилам | `CANCELLED` | Отмена подтверждена и записана |

События могут приходить не по порядку. Сначала событие сохраняется, затем текущее состояние пересчитывается по истории и правилам переходов. Устаревшее событие `document_sent` никогда не понижает уже подписанный (`SIGNED`) документ.

## 8. Сбои и восстановление

- `401 invalid_client` — неверный API-ключ: повторы прекращаются, администратор интеграции получает уведомление, ключ исправляется или меняется.
- `401 unauthorized` — токен отсутствует или истёк (30 дней): обновляется документированным способом, только если это безопасно для текущей сессии документа. Нельзя пересоздавать документ ради нового токена.
- HTTP `200` с телом `status: 0` — логическая ошибка: смотрится `message` (после маскирования), успехом по одному коду HTTP это не считается.
- Таймаут после запроса создания — `SUBMISSION_UNKNOWN`: проверить через интерфейс провайдера, официальный запрос статуса или оператора. Слепой повтор запрещён.
- Webhook не пришёл — Documentolog повторяет доставку в течение примерно суток; JanaМен сверяет ожидающие документы сама, если есть поддерживаемый запрос статуса, или поднимает ручную проверку после заданного порога.
- Не скачивается файл — проверить, что приложен тот же Bearer-токен, он не истёк, хост в списке разрешённых и есть право на этот документ. Подписанный файл нельзя показывать другому сотруднику.
- Требуемая конфигурация подписи не поддерживается — отправка останавливается и передаётся HR или оператору; подписи и требования к получателям нельзя молча отбрасывать.

## 9. Заготовки настроек

```dotenv
DOCUMENTOLOG_ADAPTER=mock
DOCUMENTOLOG_BASE_URL=https://apibusiness.documentolog.com
DOCUMENTOLOG_API_KEY=
DOCUMENTOLOG_WEBHOOK_URL=
DOCUMENTOLOG_SENDER_IDENTIFIER=
DOCUMENTOLOG_ALLOWED_HOSTS=apibusiness.documentolog.com,business.documentolog.com
DOCUMENTOLOG_CONNECT_TIMEOUT_SECONDS=3
DOCUMENTOLOG_READ_TIMEOUT_SECONDS=15
DOCUMENTOLOG_LIVE_SEND_ENABLED=false
DOCUMENTOLOG_WEBHOOK_VERIFICATION_MODE=not_configured
```

Базовый адрес — это публичный хост из руководства вендора; тестовая среда может использовать другой. Адреса задаются для каждой среды отдельно, TLS обязателен.

## 10. Чек-лист перед запуском

- Подтвердить тариф, доступ к API, среды, актуальную версию спецификации, схемы запросов и ответов, лимиты файлов, правила идентификации отправителя и получателей, способы подписи и типы документов.
- Получить от вендора примеры ответов: успешное создание, логическая ошибка, истёкший токен, повторный запрос.
- Уточнить, есть ли идемпотентность на стороне провайдера, запрос и поиск статуса, отмена и точный способ проверки подлинности webhook.
- Подтвердить юридическое и организационное лицо отправителя и порядок подписания.
- Подтвердить, что бизнес-процесс допускает немедленную отправку (черновиков нет).
- Проверить, что ссылки на вложения недоступны посторонним и истекают через заданное время.
- Прогнать сценарий на тестовых получателях и неконфиденциальных документах до работы с реальными сотрудниками.
- Утвердить ручной регламент восстановления при неизвестном результате отправки и пропущенных webhook.

## 11. Что уже реализовано в JanaМен

Текущая интеграция — **MOCK-шлюз регистрации**, а не реальный коннектор Documentolog. Работающие компоненты, которые нужно сохранить:

- `app/integrations/outbox.py` — неизменяемый снимок заявки в момент одобрения, стабильный ключ идемпотентности, безопасный для PostgreSQL захват заданий, ограниченные повторы со случайной задержкой, подписанный запрос к шлюзу и идемпотентное применение итогового результата.
- `app/gateway/main.py`, `app/gateway/runtime.py` — машинная аутентификация HMAC, постоянная защита от повторов (nonce), асинхронные сохраняемые задания с арендой, постоянные повторы и сверка callback.
- `app/gateway/connectors.py` — детерминированный MOCK-номер документа для логического задания и управляемые сценарии отказа.
- `app/routers/internal.py` — проверка подписанных внутренних callback и защита от повторов.
- `app/integrations/recovery.py` — проверяемое HR-восстановление ошибочных заданий с обязательной причиной; ключи и содержимое задания при этом не меняются.

Статусы интеграции: `NOT_REQUIRED`, `PENDING`, `SENT`, `REGISTERED`, `FAILED`, `DEAD`. `REGISTERED` — это **не** подписанный документ в реальном Documentolog. Если регистрация не удалась, заявка остаётся одобренной.

HMAC в коде защищает только обмен между JanaМен и внутренним шлюзом. Он не доказывает, что подлинность реальных webhook Documentolog можно проверить так же. Не проверены: реальное подключение, входящий mTLS в продакшене, подлинность источника webhook и контрактные тесты вендора. HTTP-клиент «под вендора» нельзя писать наугад — после получения реального контракта расширяется существующая точка подключения коннектора в шлюзе.
